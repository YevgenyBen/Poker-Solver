# Full audit — 2026-08-23 (M101)

Third full audit of this project. The first drove M27–M34, the second
M58–M65, and the rolling diagnostic that replaced it ran nineteen rounds
(M84–M100). This one is a fresh pass over the whole product: a static
code audit, a live-play simulation against the real API, and a
performance benchmark separating what a warmed server serves from what
the first person to ask actually waits for.

Findings are ordered by what they cost a user, not by how interesting
they were to find.

---

## F19 — a malformed request cost 76 seconds to reject *(fixed)*

**Severity: high.** The worst user-facing defect this audit found.

A cold 6-max request whose preflop action path leaves four players still
to act:

```
COLD  422 in 76.2s
WARM  422 in 0.002s
```

The rejection message was correct and helpful. Reaching it required
solving the entire 6-max preflop tree — a game whose answer the
rejection never reads.

**Two causes, one shape of reasoning.** The live-player count (which
decides multiway routing) fetched the solve in order to walk a tree, and
the path-shape check sat *behind* the solve rather than in front of it.
The first carried a comment justifying itself: *"The preflop solve is
already cached, so this is a tree walk, not a second solve."* That is
true on a warm cache and precisely wrong on the first request — which is
the only one a user waits for. **"The cache makes this free" is a claim
about the second caller, not the first.**

Both now build a throwaway tree instead (`game_tree` builds children
lazily, so walking one path materialises only that path).

**76.2s → 0.1s, a 760× improvement** on the path a first-time user is
most likely to hit.

Pinned by a test that counts *solves* rather than seconds: a rejected
request must leave the expensive preflop cache empty. A wall-clock bound
would flake on a machine that drifts ~1.7× between sessions.

## F20 — the affordability guarantee was only checkable at opening
## decisions *(fixed)*

**Severity: medium.** A generalisation of F13, not a regression of it.

M95 promised that no advice ever names a bet the player cannot make, and
swept every street to prove it. The sweep only ever tested each street's
*opening* decision. One decision later the guarantee is unverifiable,
because `effective_stack_bb` does not mean the same thing at every node:

| node | `effective_stack_bb` | all-in offered |
|---|---|---|
| HU preflop open | 99.0 | `all_in:100.00` |
| HU flop opening | 97.5 | `all_in:95.00` |
| HU flop facing a bet | 85.0 | `all_in:97.50` |

Preflop it is the stack net of blinds while preflop sizes are quoted as
**total commitment**. At a street's opening decision it is the money
behind entering the street. One decision later it is the **shortest
remaining stack** once someone has bet (`entry - max(invested)`).

Every one of those is defensible poker. None of them shares a baseline
with the action sizes, so `effective_stack_bb: 85.0` sits beside
`all_in:97.50` — both correct, and not comparable. A caller cannot
answer "can I afford this?" from the response.

**Fix:** a separate `max_affordable_bb` — the largest total commitment
the acting player can make on this street — so the invariant *every size
in `strategy` ≤ `max_affordable_bb`* holds at every node on every
street, and is swept at mid-street nodes rather than only opening ones.
`effective_stack_bb` keeps its meaning; things depend on it and each
reading is individually right.

A second test asserts the two fields genuinely **differ** at the node
that motivated this, so the new field cannot decay into a copy of the
old one.

## F21 — the stale-comment detector, and why the obvious one fails
## *(shipped)*

M99 found `_advise` describing its routing as going "through
`solve_flop_turn` … shares the turn cell's cache" — eleven milestones
after M88 moved it to `solve_flop` with its own cache. Confident,
specific, wrong, and found only because someone read that function for
an unrelated reason.

The obvious detector — a regex for `M\d+ .* (now|currently|as of)` —
**flagged eight lines, all accurate, and missed the real one**, which
contains none of those words. A detector that fires on comments which
merely *sound* like claims trains you to skim its output.

`tests/test_comment_drift.py` instead flags a comment saying this code
*goes through / calls / uses* a function the enclosing function never
calls. Contrast wording ("unlike X", "used to go through X") is exempt —
those are the most valuable comments in this codebase. Matching is on
comment **blocks**, not lines, because a disclaimer routinely sits a line
above the claim it disclaims; the line-based first version
false-positived on M99's own correction note. A guard test reconstructs
the original defect and requires a hit, so the checker cannot rot into
one that never fires.

## What is healthy

Worth recording, because an audit that only lists problems misrepresents
the state of the thing.

- **Layering holds.** `config ← caches ← solving ← main`, zero
  violations. No TODO/FIXME markers, no source module without a test
  module, no uncalled public solver entry point.
- **Impossible requests are refused, with reasons.** All four probes —
  a duplicated board card, a hero card already on the board, a negative
  stack, a zero stack — return 422 with a message naming the specific
  conflict. M91's work holds.
- **The honesty signals fire correctly.** `sizing_confidence: low` on
  3/6/9-max preflop and not heads-up; `solver_confidence: low` on 9-max
  only; both present together at 9-max without either masking the other.
- **Warm performance is not the problem.** Every warm response is under
  25ms; heads-up preflop 2.3ms, 6-max preflop 2.2ms.

## Performance, normalized

Reference unit measured in the same run (0.28s), per CLAUDE.md's rule
that this machine drifts between sessions:

| spot | cold | warm | cold (units) |
|---|---|---|---|
| HU preflop | 2.66s | 2.3ms | 9.5 |
| HU flop | 9.05s | 4.5ms | 32.4 |
| HU flop mid-street | 8.37s | 20.7ms | 30.0 |
| 6-max preflop | 75.88s | 2.2ms | 271.5 |

The shape is unchanged from previous audits and is the product's central
cost fact: **cold is 1,000–34,000× warm.** Everything about the caching,
the pre-warm and the canonical library exists to keep users off the cold
path, and F19 was a case where a user paid the cold price for nothing.

## One audit check was wrong, and that is worth recording

The live-play harness flagged `no_advice` wherever `hero_in_range` was
false. Reading the code, that is a *designed signal*: hero's combo did
not survive the cap on its own weight and was force-included at the range
minimum, so a strategy exists and is honest about how the hand got there.
The harness was wrong, not the product.

It also flagged every preflop all-in as "unaffordable" — which is how
F20 was found, but as stated the check was wrong too: it assumed a shared
baseline that does not exist. It now records the pair and lets the
write-up interpret it, instead of crying wolf.

**A checker that reports a real defect for the wrong reason is still
lucky, not right.**

# Round 2 (M102) — input fuzzing

M101 probed four impossible requests and all four returned a helpful 422.
Four is not a sweep. This throws 29 malformed, contradictory and boundary
inputs at `/advise` and classifies every response.

## F23 — a typo became a confident answer to a different question
## *(fixed)*

**Severity: high.** The worst failure shape this project has, and it was
in the front door the whole time.

Pydantic ignores unknown fields by default. Measured against the real
endpoint:

```
{"hero_card": "AsAh", ...}   -> 200, hero: null
{"player": 6, ...}           -> 200, players: 2
```

The first silently drops the hand the user asked about and returns a
range chart. The second answers a **6-max question with heads-up
advice**. Neither says anything is wrong. Both look exactly like correct
responses.

Every request model now sets `extra="forbid"`, so an unknown field is a
422 naming it (`body.hero_card`, "Extra inputs are not permitted"). Safe
for the frontend, which builds its body from a typed `AdviseRequest` and
sends no extras.

**How this was found is the interesting part.** The fuzzer flagged
`position: "ZZ"` returning 200 with advice for BTN, which looked like
"position is accepted but ignored". Reading the schema, `AdviseRequest`
has **no `position` field at all** — the acting seat is derived from the
action path. So the real defect was one level up: unknown fields are
silently discarded.

## F24 — the docs described an input that does not exist *(fixed)*

CLAUDE.md's own "What it does today" read: *"Given your hole cards, the
board, **your position**, and the action so far..."*

There is no position input to `/advise`. It follows from the action
path — whoever has not yet acted is the one being advised. The wording
was wrong for long enough that **every probe written against the API
during this session sent a `position` field**, and so did six tests in
`test_api.py`. All of it did nothing, silently, and nothing could have
told anyone.

Turning on `extra="forbid"` surfaced all of them at once: 22 suite
failures, every one a test sending a field that never existed. That is
the finding proving itself.

The older `/solve` and `/solve_flop` endpoints *do* take a `position`
query parameter, and validate it — which is exactly why the confusion was
plausible.

## Deliberately not fixed: an absurd but valid stack

`stack_bb: 1e9` returns 200 and `all_in:1000000000.00`. Measured: same
solve time as 100bb, structurally correct output. There is a lower bound
(`stack_bb must be greater than small_blind`) and no upper one.

Left alone on purpose. It is absurd, not impossible; there is no
principled threshold (500bb? 1,000? 10,000?); and an invented cap could
refuse a legitimate deep-stack query. **Recording the reasoning beats
adding a magic number.**

## Both fuzz results were wrong before they were right

Worth recording, because the fuzzer produced two confident and opposite
falsehoods in one session.

**First run: three "unhelpful" 422s** — `Unknown rank: '1'`,
`Unknown suit: 'x'`. Those messages name the problem precisely; the
classifier's word list simply lacked "rank" and "suit".

**Second run: a perfect 31/31 clean.** Also false. The fuzzer's base
body still contained `position="BTN"`, which `extra="forbid"` had just
made invalid — so every case returned 422 for that reason instead of the
one under test. A clean sweep that proved nothing.

M101 recorded that *a checker reporting a real defect for the wrong
reason is lucky, not right*. This is the mirror image: **a checker
reporting success for the wrong reason is worse, because nobody
investigates a pass.**

Corrected totals: **28 clean 422s, 0 crashes, 0 wrong 200s** across 29
malformed inputs, plus the one absurd-stack case above.

# Round 3 (M103) — driving the five untested UI tabs

M94 drove the Advisor in a browser for the first time. The other five
tabs had never been opened by anything but a human, and every frontend
test stubs `fetch`, so nothing had ever confirmed they talk to the real
API at all.

## All five work

| tab | result |
|---|---|
| Preflop Ranges | `GET /solve/100` → 200, full 169-hand grid |
| Equity Calculator | **AA vs KK = 82.0% / 18.0%** — matches the known ~82.4% |
| Flop Solver | solves in 0.18s, and labels untrained combos **"low data"** |
| Cached Flop Solver | live solve **327.35ms**, suit-shuffled board **0.30ms** |
| Multiway Flop Solver | 3-max solve in 0.27s, "low data" labels present |

Two things worth recording beyond "it works".

**The canonical-reuse contract is confirmed end to end in the UI for the
first time.** Solving `Jh7d2c` live took 327.35ms; shuffling the suits to
`Js7h2d` and solving again reported *"Cache hit … 0.30ms"* against the
same canonical form `2c7dJh`. That is M20/M21's central claim — a board
that is merely a suit relabelling of a solved one hits instantly —
demonstrated through the real product rather than a test fixture.

**The honesty signals reach the demo tools too.** Combos with an exactly
uniform 33/33/33 strategy carry a "low data" label in both the Flop
Solver and the Multiway Flop Solver. M82's lesson was that a correctness
signal no consumer reads is not a correctness signal; these consumers
read it.

## F25 — nothing verified the app was served at all *(fixed)*

The sweep found no defect in the tabs. It found one underneath them: the
entire suite talks to `/advise` and `/solve` directly and **never
requests the page a user opens**. If `frontend/dist` went missing, or the
catch-all static mount stopped being registered last and began
swallowing API routes, every tab would break at once and the suite would
stay green.

Two tests now cover it: the app shell is served with a bundle reference,
and `/solve/100` still returns `application/json` rather than HTML. The
second matters because the mount is registered last **on purpose**, and
"on purpose" is the kind of ordering a later edit reshuffles without
noticing — the resulting breakage would look like a frontend bug.

The shell test skips when `frontend/dist` is absent rather than failing;
a fresh clone has not run `npm run build`, and a test that punishes that
gets marked xfail and stops meaning anything.

# Round 4 (M104) — concurrency and memory

The two properties a unit suite structurally cannot see: it never issues
two requests at once, and it clears caches between cases. Both had
milestones behind them (M92 single-flight, M93 bounded caches) and
neither had been checked since.

## F26 — the thundering herd M92 missed *(fixed)*

**Severity: high.**

Measured through the real endpoint, counting actual `solve_preflop`
calls rather than inferring from wall clock:

| | solves | time |
|---|---|---|
| before | **8** | 24.21s |
| after | **1** | 10.44s |

`_get_or_solve_preflop_raw` still used check-then-compute. Every thread
checked the cache, found it empty, and solved. M92 replaced this pattern
everywhere it found it and missed this one — the heads-up preflop solve
that every heads-up **postflop** request depends on first, so any burst
of cold traffic paid for it N times.

Two reasons it survived, both structural rather than careless. The suite
never issues two requests at once, so concurrency is invisible to it. And
duplicated work leaves no trace from a single caller: every response is
correct, just paid for repeatedly.

The regression test **counts solves rather than timing**, so it states
the property directly and cannot flake on a machine that drifts ~1.7x.
Verified by mutation: restoring the old code makes it report *"6 preflop
solves ran for 6 concurrent requests"*.

## F27 — two unbounded caches keyed on request input *(fixed)*

M93 bounded thirteen caches and deliberately left two alone, justified
as: *"at most a few dozen entries ever exist, they cost 75-140s each to
rebuild, and the startup pre-warm fills them on purpose."*

Every clause is true of the entries the **pre-warm** creates. None of it
is true of the **key**:

```
_multiway_cache      key = (round(stack_bb), players)
_preflop_raw_cache   key = (round(stack_bb), iterations)
```

`stack_bb` comes from the request. A client walking stack depths mints a
new entry per integer depth, forever — measured at **0.152 MB of heap per
distinct depth**.

**And it composes with a finding that was correct in isolation.** M102
measured `stack_bb: 1e9` as absurd-but-valid and deliberately left it
uncapped: the response is structurally right, and no principled ceiling
exists. That judgement still holds on its own. Feeding an unbounded cache
keyed on that value, it becomes a memory-exhaustion path. **Neither
finding is a defect alone.** That is the part worth carrying forward —
this audit has been finding defects in seams, and this one is in the seam
between two decisions that were each individually right.

Bounded at 64 (multiway, expensive to rebuild) and 128 (preflop_raw).
Verified: 500 distinct depths collapse to 64 and 128 entries.

The test asserts the invariant over **every module-level cache** rather
than naming the two that were wrong, because the next cache added will be
wrong the same way. `multiway_equity` is exempted explicitly, with its
reason — it is keyed by the hand pool, a config constant, so its key
space is one entry. An allowlist entry has to stay a decision, not a
shrug.

## What is healthy

- **Bounded caches stayed bounded.** Nothing exceeded its `maxsize` under
  40 distinct requests; the ceilings M93 set are holding.
- **No errors under 8-way concurrency.** All eight requests returned 200
  with correct content; the defect was cost, never correctness.

# Round 5 (M105) — the hand evaluator, exhaustively

Every equity number in this project is a count of how often one hand
outranks another, and every strategy is derived from those counts. A
ranking bug does not announce itself — it makes some spots quietly wrong.
The 22 existing tests were example-based.

## No defect found

| check | scope | result |
|---|---|---|
| category census | **all 2,598,960 hands** | all 9 published frequencies exact |
| vectorized vs scalar (5-card) | **all 2,598,960 hands** | ordering *and* ties agree |
| best-of-seven vs brute force | 40,000 hands x 21 subsets | zero disagreements |
| vectorized 7-card ordering | 40,000 hands | agrees with brute force |

The foundation is sound. That is worth stating positively: the multiway
sizing defect (R17) cannot be blamed on hand evaluation, and neither can
the equity noise (R17's ±55bb).

## What shipped

The census is now a permanent test — **2.7 seconds for all 2,598,960
hands**, because it runs through the vectorized path, which is also the
path every equity computation uses. It checks against the *published*
category frequencies rather than anything this codebase produced, which
is the point: an evaluator cannot be validated against numbers it
generated itself.

**Verified by mutation:** removing the wheel-straight rule (A-2-3-4-5)
makes the census fail. A tiebreak-only corruption does *not* — categories
are unchanged — and is caught by the ordering tests instead. The two
guards are complementary, and each was checked against a mutation the
other cannot see.

## Two corrections to my own work here

**My first mutation didn't mutate.** I wrote the wheel check as
`values == {14, 2, 3, 4, 5}`; this codebase represents an ace as **12**,
with the wheel handled by adding `-1`. The mutation was inert, the tests
passed, and I briefly read that as "the census is blind to this". A
mutation check that does not mutate proves nothing — the same failure
shape as R2's fuzzer scoring a meaningless 31/31.

**And the fix I made in response was aimed at a gap that wasn't there.**
I stratified the cross-evaluator sample to force rare categories, on the
theory that uniform sampling missed the wheel. The real census caught it
all along. The stratification is kept — forcing every category is a
better sampling design regardless, and it costs 0.13s — but it was
justified by a measurement error, and the honest record is that it
**overlaps four pre-existing tests** rather than covering something new.

The genuinely new guard is the exhaustive census.

# Round 6 (M106) — equity, and an audit that was wrong about it

R5 verified hand evaluation exhaustively. Equity is the layer directly
above it — every strategy is derived from equity numbers, and R17 measured
the multiway estimator carrying ±55bb of noise at 50 samples.

## No defect found. My reference data had three.

The first pass checked heads-up equity against published all-in figures
and flagged three matchups outside tolerance, the worst by **21 percentage
points**:

```
77 vs 65s   published 0.606   measured 0.820   delta +21.4pp
```

That looks like a serious engine bug. It was my number. 65s has **both
cards below a seven**, so the pair is a large favourite; 0.606 is the
figure for a pair facing *overcards*.

Settled by enumerating every one of the C(48,5) = 1,712,304 boards —
ground truth needing no external table at all:

| matchup | exact | Monte Carlo 200k | error |
|---|---|---|---|
| 77 vs 65s | **0.8184** | 0.8202 | +0.18pp |
| AA vs KK | 0.8264 | 0.8270 | +0.06pp |
| AKs vs QJs | **0.6595** | 0.6593 | −0.03pp |
| A5s vs KQo | **0.5995** | 0.5998 | +0.03pp |

Monte Carlo tracks exact enumeration to within 0.18pp everywhere. **All
three "failures" were the reference table.** Two layers now verified
clean: hand evaluation (R5) and equity (here).

The symmetry check also "failed" — `equity(a,b) + equity(b,a)` came to
0.9972 rather than 1. That was a `> 1e-9` threshold applied to two
*independently sampled* estimates; the deviation is well inside one
standard error. An exact assertion there measures the RNG, not the
property.

## The lesson, which is R5's one layer up

R5 validated hand-eval categories against published frequencies and that
was sound: category counts are exact combinatorial facts, unambiguous and
safe to quote. Equity is **not** like that — it is matchup- and
suit-configuration dependent, and I got three of thirteen wrong from
memory.

**Ground truth a repository can regenerate beats a number recalled from
outside it.** The permanent tests therefore freeze values produced by
enumeration, and keep the enumerator alongside them so the constants can
be re-derived rather than trusted. A separate guard re-runs one
enumeration, because if `deal_two_hands` ever assigns different concrete
cards the frozen numbers quietly stop describing what it returns while
every test using them keeps passing.

## What each guard actually catches

Verified by mutation, not asserted:

- Awarding ties to one player instead of splitting → caught by the
  **symmetry** test, and *not* by the absolute-value comparison, because
  ties are rare enough in these matchups that equity moves less than the
  1pp tolerance.
- An equity-shifting modelling error (suitedness, board size) → caught by
  the absolute-value comparison.

Complementary, and now demonstrated to be.

Cost tuned from 105s to 54s. The seeds are fixed, so these are
deterministic rather than merely unlikely to flake.

# Round 7 (M107) — two live implementations of the same question

`api/solving.py` claims `/advise` is "a unified FRONT DOOR, not a second
implementation to keep in sync", and that it "deliberately delegates
rather than reimplements". That is testable, the deprecated routes are
still live and reachable, and nothing tested it.

## No defect. Both properties hold exactly.

**Cross-endpoint agreement.** `/solve_flop_from_path` and `/advise`, same
spot, caches cleared between:

| spot | position | pot | eff. stack | combo set | worst strategy delta |
|---|---|---|---|---|---|
| raise + call | same | same | same | same | **0.0** |
| limped | same | same | same | same | **0.0** |
| 3bet pot | same | same | same | same | **0.0** |

Not approximately — identically. Delegation means the same solve, so
anything other than 0.0 would mean a second implementation had appeared.

**Determinism.** The same request twice with caches cleared in between —
so the second genuinely re-solves — is bit-identical at heads-up preflop,
flop, mid-street flop, and 3-max preflop. Without the cache clearing this
would pass trivially by reading one solve twice; what it actually rules
out is accumulated state, where advice would depend on whatever the
server did beforehand.

## Both guards checked by mutation

- Giving `/advise`'s flop cell a different iteration budget from its
  sibling → **all three** consistency cases fail.
- Making the sampled solver's seed depend on call order → the **3-max**
  determinism case fails, and the heads-up cases do not, because those
  use the exact solver. That is why 3-max is in the parametrisation:
  it is the only one of the four that guards sampled solving.

## Diminishing returns, stated plainly

Rounds 5, 6 and 7 found **no defects** — hand evaluation, equity, and
cross-endpoint consistency all verified clean. Rounds 1–4 found six, and
every one was in a seam: cost (a 76s rejection, a duplicated solve),
contract (a guarantee checkable only where it was tested, a typo becoming
confident advice), composition (two correct decisions combining into a
memory-exhaustion path), and reachability (a UI nothing confirmed was
served).

The engine layers are sound and now have exhaustive guards. **The
remaining known-wrong thing is the one this audit cannot fix by
testing** — M98's structural sizing defect, which needs solved postflop
continuation values, an architectural milestone M100 established cannot
be justified on a heuristic stand-in.

Worth recording so the next round is not chosen by habit: further
value is more likely in seams that have not been probed at all
(`derive_ranges_from_path`'s reach multiplication, behaviour when a solve
raises mid-request) than in re-verifying layers already shown correct.

# Round 8 (M108) — the two seams R7 named

R7 recorded that further value was likelier in seams never probed than in
re-verifying layers already shown correct, and named two:
`derive_ranges_from_path`'s reach multiplication, and behaviour when a
solve raises mid-request. This is those two.

## No defect in either

**A failing solve behaves correctly.** The failure mode that would matter
here is not an ugly error — it is a **200 with fabricated advice**, which
is exactly what this codebase's honesty machinery exists to prevent. It
does not happen: the exception propagates as a server error, the server
recovers, and — checked separately, because "the next request returns
200" is not the same claim — the post-failure answer is **bit-identical**
to a clean one computed before any failure. No partial entry survives.

Deliberately not "fixed" into a friendly 422. Dressing an unexpected
solver bug up as a validation failure would hide it.

**Reach multiplication is doing real work.** It turns "here is what
happened" into "here is what each player can hold", and every postflop
solve is seeded from its output, so a wrong range makes every downstream
strategy wrong while looking normal:

| path | position | AA | KK | T2o | J4o |
|---|---|---|---|---|---|
| limped | BTN (limper) | 0.0055 | 0.0025 | 0.0107 | 0.0107 |
| raise + call | BTN (raiser) | 0.0083 | **0.0128** | **0.00002** | 0.0002 |
| 3bet pot | BB (3-bettor) | **0.036** | **0.036** | 0.0 | 0.0 |

The raiser weights KK **640x** above T2o; the three-bettor is more
concentrated still; the limper tilts slightly *toward* trash, which is
right — strong hands raise. No negative weights, and no two paths derive
the same range.

The zeros are correct rather than suspicious: BB holds no AA in a limped
pot because AA always raises, and BTN holds none in a three-bet pot
because AA always four-bets. Those are consequences of the strategy, not
gaps in the derivation.

## Asserted comparatively, on purpose

The guards compare lines against each other — three-bettor stronger than
raiser, raiser stronger than limper — rather than pinning weights. Exact
values depend on the preflop solve's budget and would make the test a
brittle snapshot; the ordering is what must hold, and it is what collapses
if reach multiplication stops happening.

Verified by mutation: removing the conditioning
(`reach[actor][hand] * freqs[hand]` → `reach[actor][hand]`) fails both
range guards.

## A third inert injection, caught before it became a conclusion

The failure probe initially patched `api.solving.solve_flop` and the
request returned **200** — which reads as "a failing solve returns
confident advice", a serious finding. It was not: the flop path solves
through `poker_solver.library`, so the patch never intercepted anything.

That is the third time this session an instrument produced a confident
result while doing nothing (M105's ace-value mutation, M102's fuzzer base
body, this). The pattern is now explicit enough that the shipped test
carries its own guard — it asserts the injected failure actually fired,
and says so in the message.

# Round 9 (M109) — cache key completeness

M76 found that `hero_cards` changed the solved *pool* but was absent from
the path-query cache keys. On a shared server the first asker for a spot
fixed the answer, and everyone after received advice for someone else's
hand — correct-looking, and wrong. Nothing has since checked whether any
other field has the same problem.

It is **structurally invisible** to the rest of the suite: the fixture
clears caches between tests, so every test is always the first caller.

## No defect. All six fields reach the key.

| field | changes the answer? | warm matches cold? |
|---|---|---|
| `stack_bb` | yes | yes |
| `board` | yes | yes |
| `hero_cards` | yes | yes |
| `preflop_action_path` | yes | yes |
| `flop_action_path` | yes | yes |
| `players` | yes | yes |

The method distinguishes "missing from the key" from "genuinely has no
effect", which a naive comparison cannot: run the variant **warm** (after
a baseline has populated the cache) and **cold** (alone). Identical warm
and cold means the key carries the field. Differing means the warm
request was served a previous caller's solve.

## Verified against the original bug

Reintroducing M76's exact defect — making `_hero_cache_component` return
`None` — produces:

```
{"field": "hero_cards", "warm_matches_cold": false,
 "VERDICT": "KEY INCOMPLETE — warm answer differs from cold"}
```

on that field **and only that field**. The shipped test fails the same
way, on the `hero_cards` case alone. After three inert instruments this
session, the clean result is only worth reporting because the probe was
shown to detect the thing it exists for.

The parametrisation also carries a guard against passing vacuously: if a
field simply had no effect, warm and cold would agree for that reason, so
a separate test asserts that changing the board really does change the
answer on a cold cache.

# Round 10 (M117) — the betting tree, exhaustively

Nine rounds verified other layers while *assuming* this one. Every
answer the solver gives is an expectation over paths through
`game_tree.py`, so a tree that encodes something other than poker
corrupts everything downstream while every other check stays green.

Eight legality invariants, checked at every node of whole trees across
38 configs — 2-6 players, raise caps 1-4, stacks from 2bb to 100bb,
postflop SPRs from 0.2 to 16:

| invariant | what it rules out |
|---|---|
| pot conservation | a pot that does not equal what players put in |
| stack bound | anyone investing more than they have |
| **no side pots at showdown** | live players committing different amounts |
| actor eligibility | a folded or all-in player asked to act |
| fold availability | a fold offered with nothing to call, or withheld facing a bet |
| action closes | a player asked to act twice with no raise between |
| label matches money | `raise:7.5` that does not move 7.5 |
| monotone commitment | money leaving the pot, or a non-actor's stack moving |

**Result: 26,354 nodes, 14,434 terminals, 11,784 showdowns, zero
violations.**

The load-bearing one is **no side pots**. M23 proved it from
construction and built `query_strategy_from_path` on it; M35's plan
generalized the proof to N players on the strength of that argument.
Nothing had ever checked it. It holds.

## F28 — a guard that cannot fire, and why to keep it

`_reopened_order` excludes players who are already all-in. Instrumented
over 1,880 calls across twelve configs it **never excluded anybody** —
an injected mutation deleting the clause entirely was the one mutation
of four these checks did not catch.

It is unreachable by construction, and the reason is not obvious: once
any player is all-in, `current_bet` equals `stack_bb`, so every
remaining player's `to_call` and `remaining_stack` are the same number,
and `_build` offers a raise only when `remaining_stack > to_call`
*strictly*. No raise can follow an all-in, and `_reopened_order` is only
called from a raise.

Not deleted. It is the guard that would matter the moment stacks stopped
being equal — precisely the assumption the no-side-pots proof rests on.
Documented in place, with `test_no_raise_is_offered_once_anyone_is_all_in`
pinning the property that makes it dead.

## F29 — a stack shorter than the big blind *(fixed)*

`GameConfig` required `stack_bb > small_blind`. The big blind is posted
unconditionally, so a stack between the two blinds built a tree whose
root already had `invested["BB"] > stack_bb`, and every pot below it
counted chips nobody had. The overstatement is exactly
`2 * (big_blind - stack_bb)`:

| stack | worst phantom chips | as % of the real pot |
|---|---|---|
| 0.51bb | 0.98 | **96.1%** |
| 0.6bb | 0.80 | 66.7% |
| 0.75bb | 0.50 | 33.3% |
| 0.9bb | 0.20 | 11.1% |
| 0.99bb | 0.02 | 1.0% |
| 1.0bb | 0.00 | 0% |

Reachable: `POST /advise {"stack_bb": 0.6}` returned **200** with a full
169-class strategy. `stack_bb` carries no numeric bound in
`api/schemas.py` by design — the comment there says `stack_bb <= 0` is
"caught for free by GameConfig's own `__post_init__`", which was true
and turned out to be the wrong bound. Now `stack_bb >= big_blind`, and a
0.6bb request is a 422.

Nobody plays 0.6bb. The reason this matters is the shape, not the
depth: it is F23's shape again — a confident 200 answering a question
nobody asked.

**And raising the bound was not the whole fix.** At exactly
`stack_bb == big_blind` the BB is all-in from posting and has no
decision — but `_build`'s opening `to_act` listed every position
unconditionally, so the big blind got a decision node whose one action
was a call it had no chips left to make. The all-in filter existed only
in `_reopened_order`, which F28 shows is reached only from a raise, and
no raise can follow an all-in — so it could never have covered this.
`build_game_tree` now filters the opening `to_act` too. Verified clean
at 2/3/4/6 players across 1.0-100bb; the new bound is a boundary the
tree actually handles, not just one it stops rejecting.

## The two guards that were never exercised

The fix failed its own new test, which is how the second half of F29
surfaced. `test_config_rejects_stack_not_greater_than_small_blind` built
`GameConfig(stack_bb=0.5, small_blind=0.5, raise_sizes=())` and asserted
a bare `ValueError` — but `raise_sizes=()` with the default
`max_raises=4` is *itself* invalid, and that check runs first. The test
had never reached the guard it named. Same for
`test_config_rejects_nonpositive_blinds`.

Both now pass `max_raises=1` and `match=` the guard they mean. Swept the
rest of the suite: 70-odd other `raise_sizes=()` uses, every one
correctly paired with `max_raises=1`. These two were the only inert ones.

Third time this audit has found a check that could not fail (M105's
inert mutation, M108's inert injection, now these) — and the third time
it surfaced only because something was made to fail on purpose.
