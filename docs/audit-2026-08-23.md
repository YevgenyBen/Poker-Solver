# Full audit — 2026-08-23 (M101)

Third full audit of this project. The first drove M27–M34, the second
M58–M65, and the rolling diagnostic that replaced it ran nineteen rounds
(M84–M100). This one is a fresh pass over the whole product: a static
code audit, a live-play simulation against the real API, and a
performance benchmark separating what a warmed server serves from what
the first person to ask actually waits for.

Findings are ordered by what they cost a user, not by how interesting
they were to find.

---

## F19 — a malformed request cost 76 seconds to reject *(fixed)*

**Severity: high.** The worst user-facing defect this audit found.

A cold 6-max request whose preflop action path leaves four players still
to act:

```
COLD  422 in 76.2s
WARM  422 in 0.002s
```

The rejection message was correct and helpful. Reaching it required
solving the entire 6-max preflop tree — a game whose answer the
rejection never reads.

**Two causes, one shape of reasoning.** The live-player count (which
decides multiway routing) fetched the solve in order to walk a tree, and
the path-shape check sat *behind* the solve rather than in front of it.
The first carried a comment justifying itself: *"The preflop solve is
already cached, so this is a tree walk, not a second solve."* That is
true on a warm cache and precisely wrong on the first request — which is
the only one a user waits for. **"The cache makes this free" is a claim
about the second caller, not the first.**

Both now build a throwaway tree instead (`game_tree` builds children
lazily, so walking one path materialises only that path).

**76.2s → 0.1s, a 760× improvement** on the path a first-time user is
most likely to hit.

Pinned by a test that counts *solves* rather than seconds: a rejected
request must leave the expensive preflop cache empty. A wall-clock bound
would flake on a machine that drifts ~1.7× between sessions.

## F20 — the affordability guarantee was only checkable at opening
## decisions *(fixed)*

**Severity: medium.** A generalisation of F13, not a regression of it.

M95 promised that no advice ever names a bet the player cannot make, and
swept every street to prove it. The sweep only ever tested each street's
*opening* decision. One decision later the guarantee is unverifiable,
because `effective_stack_bb` does not mean the same thing at every node:

| node | `effective_stack_bb` | all-in offered |
|---|---|---|
| HU preflop open | 99.0 | `all_in:100.00` |
| HU flop opening | 97.5 | `all_in:95.00` |
| HU flop facing a bet | 85.0 | `all_in:97.50` |

Preflop it is the stack net of blinds while preflop sizes are quoted as
**total commitment**. At a street's opening decision it is the money
behind entering the street. One decision later it is the **shortest
remaining stack** once someone has bet (`entry - max(invested)`).

Every one of those is defensible poker. None of them shares a baseline
with the action sizes, so `effective_stack_bb: 85.0` sits beside
`all_in:97.50` — both correct, and not comparable. A caller cannot
answer "can I afford this?" from the response.

**Fix:** a separate `max_affordable_bb` — the largest total commitment
the acting player can make on this street — so the invariant *every size
in `strategy` ≤ `max_affordable_bb`* holds at every node on every
street, and is swept at mid-street nodes rather than only opening ones.
`effective_stack_bb` keeps its meaning; things depend on it and each
reading is individually right.

A second test asserts the two fields genuinely **differ** at the node
that motivated this, so the new field cannot decay into a copy of the
old one.

## F21 — the stale-comment detector, and why the obvious one fails
## *(shipped)*

M99 found `_advise` describing its routing as going "through
`solve_flop_turn` … shares the turn cell's cache" — eleven milestones
after M88 moved it to `solve_flop` with its own cache. Confident,
specific, wrong, and found only because someone read that function for
an unrelated reason.

The obvious detector — a regex for `M\d+ .* (now|currently|as of)` —
**flagged eight lines, all accurate, and missed the real one**, which
contains none of those words. A detector that fires on comments which
merely *sound* like claims trains you to skim its output.

`tests/test_comment_drift.py` instead flags a comment saying this code
*goes through / calls / uses* a function the enclosing function never
calls. Contrast wording ("unlike X", "used to go through X") is exempt —
those are the most valuable comments in this codebase. Matching is on
comment **blocks**, not lines, because a disclaimer routinely sits a line
above the claim it disclaims; the line-based first version
false-positived on M99's own correction note. A guard test reconstructs
the original defect and requires a hit, so the checker cannot rot into
one that never fires.

## F22 — two constants with no measured justification *(fixed)*

`api/config.py` documents every tunable with the numbers that chose it.
Two did not: `DEFAULT/MAX_MULTIWAY_TURN_PATH_QUERY_FLOP_ITERATIONS`,
which inherited their values by analogy with the flop sibling. That
reasoning is sound and it is still not a measurement, and the comment now
says which is which rather than leaving the gap silent.

## What is healthy

Worth recording, because an audit that only lists problems misrepresents
the state of the thing.

- **Layering holds.** `config ← caches ← solving ← main`, zero
  violations. No TODO/FIXME markers, no source module without a test
  module, no uncalled public solver entry point.
- **Impossible requests are refused, with reasons.** All four probes —
  a duplicated board card, a hero card already on the board, a negative
  stack, a zero stack — return 422 with a message naming the specific
  conflict. M91's work holds.
- **The honesty signals fire correctly.** `sizing_confidence: low` on
  3/6/9-max preflop and not heads-up; `solver_confidence: low` on 9-max
  only; both present together at 9-max without either masking the other.
- **Warm performance is not the problem.** Every warm response is under
  25ms; heads-up preflop 2.3ms, 6-max preflop 2.2ms.

## Performance, normalized

Reference unit measured in the same run (0.28s), per CLAUDE.md's rule
that this machine drifts between sessions:

| spot | cold | warm | cold (units) |
|---|---|---|---|
| HU preflop | 2.66s | 2.3ms | 9.5 |
| HU flop | 9.05s | 4.5ms | 32.4 |
| HU flop mid-street | 8.37s | 20.7ms | 30.0 |
| 6-max preflop | 75.88s | 2.2ms | 271.5 |

The shape is unchanged from previous audits and is the product's central
cost fact: **cold is 1,000–34,000× warm.** Everything about the caching,
the pre-warm and the canonical library exists to keep users off the cold
path, and F19 was a case where a user paid the cold price for nothing.

## One audit check was wrong, and that is worth recording

The live-play harness flagged `no_advice` wherever `hero_in_range` was
false. Reading the code, that is a *designed signal*: hero's combo did
not survive the cap on its own weight and was force-included at the range
minimum, so a strategy exists and is honest about how the hand got there.
The harness was wrong, not the product.

It also flagged every preflop all-in as "unaffordable" — which is how
F20 was found, but as stated the check was wrong too: it assumed a shared
baseline that does not exist. It now records the pair and lets the
write-up interpret it, instead of crying wolf.

**A checker that reports a real defect for the wrong reason is still
lucky, not right.**
